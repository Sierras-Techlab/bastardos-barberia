# Local Authentication with Supabase Database Design

**Date:** 2026-08-07
**Status:** Approved
**Project:** Bastardos Barbería administrative dashboard

## Objective

Implement a deliberately simple employee authentication system in the Next.js application while using Supabase only as PostgreSQL storage. Supabase Auth is explicitly out of scope. Administrators assign passwords, usernames are generated from employee names, and all database access remains server-side.

## Scope

This slice includes local username/password authentication, persistent revocable database sessions, fixed `owner`, `admin`, and `employee` roles, administrative user APIs, login UI integration, private-route protection, copy-and-paste Supabase SQL, a controlled first-owner bootstrap, and living project documentation.

It excludes Supabase Auth, public registration, invitations, email recovery, MFA, social login, a user-management frontend, fine-grained permissions, and persistence for sales, products, customers, or services.

## Chosen Architecture

### Application boundary

The Next.js 16 App Router application is the only application-facing API. Browser code never queries Supabase directly. Route Handlers call a server-only data-access layer that uses `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SECRET_KEY` through `@supabase/supabase-js`.

The secret key bypasses Row Level Security and is therefore limited to modules marked server-only. Every privileged operation authenticates the current local session and authorizes its role before executing database mutations.

### Authentication

Passwords are hashed with Argon2id using OWASP-compatible parameters. Passwords are accepted only by server Route Handlers, never logged or returned, and never persisted in plaintext.

Login accepts username and password. Five consecutive failures lock that account for 15 minutes. Failure responses use the same public message whether the username is unknown, the password is wrong, or the account is temporarily locked. Success resets failure counters and records `last_login_at`.

### Sessions

Successful login creates a random 32-byte opaque token. The raw token exists only in an `HttpOnly` cookie; PostgreSQL stores only its SHA-256 hash. Sessions have a fixed 12-hour lifetime and can be revoked immediately.

The cookie uses `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` outside local development. Authentication tokens never enter `localStorage` or JSON responses.

Each secure operation loads the session by token hash and confirms that it is unrevoked, unexpired, and owned by an active user. Password resets and deactivation revoke every session for the target user.

### Authorization

- `owner`: full access.
- `admin`: full access in this version.
- `employee`: authenticated operational access with no user administration.

`src/proxy.ts` performs optimistic redirects based on cookie presence; it is not a security boundary. Route Handlers and server-side data-access functions perform authoritative database-backed checks.

Administrative invariants are:

- Only `owner` and `admin` access `/api/admin/*`.
- A user cannot deactivate their own account.
- The last active `owner` cannot be deactivated or assigned another role.
- Users are deactivated rather than physically deleted.

## Username Rules

The database generates usernames; administrators never choose them. It trims names, lowercases them, removes accents with PostgreSQL `unaccent`, removes remaining non-ASCII alphanumeric characters from each part, and joins the parts with a period.

The application rejects values without any Unicode letter or number as an early usability check. PostgreSQL remains authoritative for transliteration; a value that still normalizes to an empty component is returned as a safe 400 validation error.

- `Juan` + `Pérez` becomes `juan.perez`.
- `María` + `De la Cruz` becomes `maria.delacruz`.
- A second `Juan Pérez` becomes `juan.perez2`, then `juan.perez3`.

A transaction-scoped advisory lock serializes creation for the same base, while a unique constraint remains the final invariant. The username remains stable when display names are edited so a correction cannot silently change a login credential.

## Database Design

### `public.roles`

| Column | Type | Rules |
|---|---|---|
| `id` | `smallint` | Primary key |
| `name` | `text` | Unique fixed role name |
| `created_at` | `timestamptz` | Not null, defaults to `now()` |

Stable IDs are owner `1`, admin `2`, and employee `3`.

### `public.users`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key, defaults to `gen_random_uuid()` |
| `first_name` | `text` | Trimmed, 1–80 characters |
| `last_name` | `text` | Trimmed, 1–80 characters |
| `username` | `text` | Unique, generated by trigger |
| `password_hash` | `text` | Not null |
| `role_id` | `smallint` | References `roles(id)` |
| `is_active` | `boolean` | Defaults to true |
| `failed_login_attempts` | `smallint` | Defaults to zero, non-negative |
| `locked_until` | `timestamptz` | Nullable |
| `last_login_at` | `timestamptz` | Nullable |
| `password_changed_at` | `timestamptz` | Defaults to `now()` |
| `created_by` | `uuid` | Nullable self-reference, `ON DELETE SET NULL` |
| `created_at` | `timestamptz` | Defaults to `now()` |
| `updated_at` | `timestamptz` | Maintained by trigger |

### `public.sessions`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key, defaults to `gen_random_uuid()` |
| `user_id` | `uuid` | References `users(id)`, `ON DELETE CASCADE` |
| `token_hash` | `text` | Unique |
| `expires_at` | `timestamptz` | Not null |
| `revoked_at` | `timestamptz` | Nullable |
| `last_seen_at` | `timestamptz` | Defaults to `now()` |
| `created_at` | `timestamptz` | Defaults to `now()` |

Indexes support username lookup, user filtering, token lookup, and expired-session cleanup. RLS is enabled on all tables; `anon` and `authenticated` receive no table privileges or policies. Trigger functions use an empty search path and schema-qualified objects.

Failed-login increments and final-owner profile transitions run in locked database functions. This keeps the five-attempt lockout and the requirement for one active owner correct even when concurrent requests pass application-level checks at the same time.

## API Contract

Success uses `{ data: ... }`; failure uses `{ error: { code: string, message: string, fields?: object } }`.

### Authentication

- `POST /api/auth/login`: accepts `username` and `password`, sets the cookie, and returns the safe current-user DTO. Invalid credentials return 401; invalid input returns 400.
- `POST /api/auth/logout`: revokes the current session when present, always clears the cookie, and is idempotent.
- `GET /api/auth/me`: returns the safe current-user DTO or 401.

### Administration

All endpoints require an active owner or admin.

- `GET /api/admin/users`: paginated listing with `page`, `pageSize`, `search`, `role`, and `status` filters.
- `POST /api/admin/users`: accepts `firstName`, `lastName`, `password`, and `roleId`; returns the generated username.
- `GET /api/admin/users/:id`: returns one safe administrative user DTO or 404.
- `PATCH /api/admin/users/:id`: updates any combination of `firstName`, `lastName`, `roleId`, and `isActive` while preserving username and enforcing invariants.
- `PUT /api/admin/users/:id/password`: stores a new hash, updates `password_changed_at`, resets failures, and revokes the target user's sessions.
- `GET /api/admin/roles`: returns the fixed roles.

## First Owner Bootstrap

SQL cannot safely produce the selected Argon2id hash. After installing the SQL, `npm run bootstrap:owner` creates the first owner using the application's password service.

The script reads `BOOTSTRAP_OWNER_FIRST_NAME`, `BOOTSTRAP_OWNER_LAST_NAME`, and `BOOTSTRAP_OWNER_PASSWORD` from the ignored environment file. It refuses to run if any application user exists, inserts an active owner, prints only the username, and instructs the operator to remove the temporary variables.

## Supabase SQL Delivery

Files under `supabase/queries/` are executed in order:

1. `001_extensions_and_roles.sql`
2. `002_users.sql`
3. `003_sessions.sql`
4. `004_functions_and_triggers.sql`
5. `005_security.sql`
6. `README.md`

Each script is ordered, documented, schema-qualified, and idempotent where PostgreSQL permits it. The README includes installation and verification queries. Supabase CLI credentials are not required.

## Application Structure

- `src/lib/supabase/admin.ts`: server-only Supabase client.
- `src/lib/auth/password.ts`: Argon2id hashing and verification.
- `src/lib/auth/username.ts`: matching TypeScript normalization for previews/tests.
- `src/lib/auth/session-token.ts`: opaque-token generation and SHA-256 hashing.
- `src/lib/auth/cookie.ts`: session-cookie policy.
- `src/lib/auth/session.ts`: session lifecycle and current-user loading.
- `src/lib/auth/authorization.ts`: authenticated and administrative guards.
- `src/lib/auth/schemas.ts`: Zod request schemas.
- `src/lib/auth/types.ts`: internal models and safe DTOs.
- `src/lib/users/repository.ts`: user persistence and filtering.
- `src/lib/users/service.ts`: user lifecycle rules.
- `src/app/api/**/route.ts`: thin HTTP adapters.
- `src/proxy.ts`: optimistic redirects only.
- `scripts/bootstrap-owner.ts`: controlled first-owner creation that reuses the application password service.

No unit combines HTTP parsing, password handling, persistence, and authorization.

## Frontend Integration

The existing username/password login form stays visually intact. Submission validates input, calls the login endpoint, displays a generic Spanish error, disables duplicate submissions, and redirects to `/` on success.

The future user-management UI is outside this slice. Its create form needs first name, last name, password, confirmation, and role. It must not request a username.

## Error Handling

- 400 for invalid input with field details.
- 401 for missing/invalid sessions and invalid credentials.
- 403 for authenticated employees accessing administration.
- 404 for missing resources.
- 409 for uniqueness or lifecycle invariant conflicts.
- 500 for unexpected errors, logged without passwords, tokens, hashes, secret keys, or full request bodies.

## Testing and Verification

Vitest covers username normalization/collisions, password validation/hashing, token hashing, session lifecycle, lock timing, role guards, owner invariants, Route Handler contracts/cookies, and login-form loading/errors/success. Final verification runs the full tests, ESLint, `git diff --check`, and a production build.
