# Persistent Products and Inventory Backend Design

**Date:** 2026-08-11
**Branch:** `feat/backend-models`
**Scope:** Persistent product catalog and auditable inventory management

## Objective

Replace the `/products` demonstration fixture and reload-scoped mutations with a server-authorized Supabase PostgreSQL backend. Preserve the current catalog, filters, metrics, responsive table/cards and management dialogs while making product creation, editing, lifecycle changes and stock adjustments durable.

This is the first delivery in the commercial-domain sequence. Products and inventory must be complete and verified before services, customers and incomes are implemented.

## SQL delivery

All product-domain SQL will live in the new ordered file `supabase/queries/008_products_inventory.sql`. Existing scripts `001` through `007` remain unchanged. The installation README will identify `008` as a prerequisite for the later sales-domain script.

The script will create its objects idempotently where practical and finish with copy/paste verification queries for tables, columns, constraints, indexes, RLS, grants and functions. The agent will not execute this script against the configured Supabase project; the user will apply it manually through Supabase SQL Editor.

## Data model

### `products`

Each product contains:

- `id`: UUID primary key generated by PostgreSQL.
- `name`: trimmed display name.
- `normalized_name`: normalized comparison key maintained by the database.
- `category`: one of `hair-care`, `styling`, `beard-care` or `fragrance`.
- `price`: non-negative integer Argentine pesos.
- `stock`: non-negative integer units currently available.
- `is_active`: whether the product may appear to employees and in new sales.
- `created_by`: non-null reference to the user who created it.
- `updated_by`: non-null reference to the user responsible for its latest profile or lifecycle change.
- `created_at` and `updated_at`: PostgreSQL timestamps.

`normalized_name` is unique across active and inactive products. Deactivating a product does not make its name reusable. Products are never physically deleted by the application because historical sales and inventory movements must retain their references.

### `inventory_movements`

Every stock mutation creates an append-only movement containing:

- `id`: UUID primary key.
- `product_id`: affected product.
- `movement_type`: `initial`, `entry`, `exit`, `sale` or `sale_void`.
- `quantity_delta`: signed non-zero unit change.
- `stock_after`: exact product stock after the mutation.
- `user_id`: authenticated actor responsible for the movement.
- `created_at`: authoritative database timestamp.

The initial product stock creates an `initial` movement when it is greater than zero. The later sales-domain script adds an `income_id` reference for `sale` and `sale_void` movements.

The current stock remains denormalized on `products` for fast catalog reads. `inventory_movements` is the immutable audit ledger. PostgreSQL functions update both within one transaction so they cannot diverge through supported application operations.

## Database operations

`008_products_inventory.sql` will expose service-role-only functions for:

- Creating a product and its optional initial-stock movement atomically.
- Applying a manual stock entry or exit while locking the product row.

An exit that exceeds current stock fails without changing either table. Product profile edits, price changes and activation changes update `updated_by` and `updated_at`. Database uniqueness remains authoritative under concurrent requests.

All new tables have RLS enabled with no browser policies. `anon` and `authenticated` receive no table or function access; only `service_role` may use the supported objects. Browser code never imports the Supabase admin client or receives its secret key.

## Authorization and application boundaries

- Owner and admin may create, edit, activate, deactivate and adjust product stock.
- Employee may list and inspect active products only.
- Every mutation authorizes again in the server service or Route Handler; hidden controls are not a security boundary.
- Audit user identifiers come exclusively from the authenticated server session and are never accepted from request JSON.

The server implementation is separated into Zod request/query schemas, database row and DTO types, a server-only repository, a domain service and thin Route Handlers. Database errors are translated into stable application errors without exposing SQL details.

## API contract

- `GET /api/products`: authenticated catalog listing. Managers receive active and inactive products; employees receive active products only.
- `POST /api/products`: manager-only product creation, including initial stock.
- `PATCH /api/products/:id`: manager-only name, category, price or active-state update.
- `POST /api/products/:id/stock-movements`: manager-only manual entry or exit.

The catalog remains bounded and loads as one collection because the existing UI performs instant client-side search, filtering, sorting and metrics. Product audit fields and inventory history are not serialized to the catalog UI in this increment.

## Frontend integration

The authenticated `/products` server page loads authorized persistent products and passes them into the existing client workspace. `ProductsView` preserves its presentation behavior but replaces in-memory-only mutations with a narrow API client.

Every mutation has a pending guard, preserves the dialog draft on failure, renders contextual validation or blocking errors and refreshes local catalog state only after a successful response. Successful operations retain the shared Sonner feedback. The demonstration badge and fixture import are removed.

Employee controls remain absent. Manager filters continue to include inactive products. Stock changes continue to flow only through the dedicated movement dialog; general product editing never changes stock.

## Validation and errors

The backend rejects:

- Empty or duplicate normalized names.
- Unsupported categories.
- Non-integer or negative prices and initial stock.
- Non-positive manual adjustment quantities.
- Stock exits larger than available stock.
- Missing, inactive or logically deleted authenticated users.
- Employee mutations.
- Missing products.

Expected conflicts use stable public error codes such as `PRODUCT_NAME_EXISTS`, `INSUFFICIENT_STOCK`, `PRODUCT_NOT_FOUND` and `FORBIDDEN`. Raw Supabase messages are logged only as sanitized operation/code pairs and are never returned to the browser.

## Testing and verification

Implementation follows test-driven development. Coverage includes:

- Zod schemas and normalized duplicate behavior.
- Database row mapping and repository calls.
- Manager authorization and employee read scope.
- Atomic product creation contract and initial movement parameters.
- Valid entries/exits and insufficient-stock failures.
- Profile and lifecycle updates with audit actors.
- Route response status, error shape and session enforcement.
- API-backed dialogs, pending guards, retry behavior and successful catalog refresh.
- Preservation of existing filters, metrics, sorting and responsive representations.

Focused tests run during each red/green cycle. Completion requires the focused suite, full `npm test`, `npm run lint`, `npm run build` and `git diff --check` to succeed. The SQL README will provide a separate manual post-install verification step for the configured Supabase project.

## Acceptance boundary

Products is complete when `/products` no longer depends on demonstration data, every supported action persists through an authorized server boundary, stock cannot become negative, inventory changes are auditable, and all automated verification passes. Applying `008_products_inventory.sql` to the remote project remains an explicit user-owned deployment step.
